# Deploying the backend and database to Render

This guide deploys the Symfony API (`backend/`) as a Docker web service and
creates a managed PostgreSQL database. Both are defined in
`render.yaml` at the **repository root** (`mobile-Lab/render.yaml`), which is
where Render looks for a Blueprint.

## What gets created

| Resource | Name | Notes |
| --- | --- | --- |
| Web service | `iot-academic-backend` | Docker image built from `backend/Dockerfile`, Free plan |
| Postgres database | `iot-academic-db` | PostgreSQL 18, database `app_db`, user `symfony`, Free plan |

The API is reachable at `https://iot-academic-backend.onrender.com` (Render may
add a suffix if the name is taken). The exact URL is shown on the service page.

On every start, the container:

1. Points Apache at the `PORT` value Render injects (normally `10000`).
2. Generates JWT keys if they do not exist (they are git-ignored).
3. Waits for the database, then runs `doctrine:migrations:migrate`.
4. Clears/warms the Symfony prod cache and starts Apache.

## Branch strategy

Keep `production` clean by treating it as a release branch only:

```
feature branches  ->  dev  ->  pre-prod  ->  production  ->  Render
   (daily work)     (integrate)  (test)      (release)       (deploy)
```

- **Never commit or push directly to `production`.**
- Promote code with PRs: `dev → pre-prod`, then `pre-prod → production`.
- `render.yaml` sets `branch: production`, so commits on `dev` or `pre-prod`
  never trigger a production deploy.
- Tag every release, for example `v1.0.0`, so you know what is live.

## Deploy steps

Production deploys from the **`production`** branch (there is no `prod` branch
in this repository). `render.yaml` must exist at the repo root on that branch.

1. Commit the deployment files on `dev`, promote to `pre-prod`, test there,
   then release to `production`.

   ```bash
   cd /home/ahmed/mobile-Lab

   # Integration
   git add render.yaml iot-academic-project
   git commit -m "chore: add Render deployment blueprint"
   git push origin dev

   # Staging
   git checkout pre-prod
   git pull origin pre-prod
   git merge dev
   git push origin pre-prod

   # Test on pre-prod before continuing, then release
   git checkout production
   git pull origin production
   git merge pre-prod
   git push origin production

   git tag -a v1.0.0 -m "First production release"
   git push origin v1.0.0
   ```

   In a team, create each promotion as a pull request so CI and review run
   before the merge.

2. In the Render Dashboard, click **New > Blueprint**.

3. Connect the GitHub repository `Ayoub-27764101/mobile-Lab` and select branch
   **`production`**.

4. Review the two resources, then click **Apply**. Render creates the database
   first, builds the Docker image, runs migrations in the container, and marks
   the deploy live once `GET /health` returns `200`.

5. Verify:

   ```bash
   curl https://iot-academic-backend.onrender.com/health
   # {"status":"ok"}

   curl -I https://iot-academic-backend.onrender.com/
   # 404 is expected: no root route is defined yet.
   ```

## Environment variables defined by the Blueprint

| Variable | Source | Purpose |
| --- | --- | --- |
| `APP_ENV` / `APP_DEBUG` | fixed | Production mode |
| `APP_SECRET` | generated by Render | Symfony secret |
| `DATABASE_URL` | from `iot-academic-db` | Internal connection string |
| `DATABASE_SERVER_VERSION` | `18` | Required by Doctrine DBAL 4 because Render's URL has no `serverVersion` |
| `JWT_PASSPHRASE` | generated by Render | Passphrase for the JWT keypair |
| `CORS_ALLOW_ORIGIN` | fixed regex | Localhost, `*.onrender.com`, Capacitor/Ionic origins |

Change `CORS_ALLOW_ORIGIN` in the Render dashboard if the Flutter web/desktop
app is served from another domain. Native mobile apps normally send no
`Origin` header, so CORS does not block them.

## JWT keys

The keypair is created in `config/jwt/` on first boot and is **not** committed.
Because the filesystem is ephemeral, a restart creates a new keypair and all
existing tokens become invalid (users simply log in again).

For stable keys, create two Render Secret Files containing the PEM contents and
set these environment variables in the dashboard:

```
JWT_SECRET_KEY=/etc/secrets/jwt-private.pem
JWT_PUBLIC_KEY=/etc/secrets/jwt-public.pem
```

The entrypoint detects those paths and skips key generation. Keep the private
key secret and generate it with:

```bash
cd backend
php bin/console lexik:jwt:generate-keypair
```

## Free plan limitations

- The web service spins down after 15 minutes of inactivity; the first request
  after that takes about a minute.
- The Free Postgres database expires **30 days** after creation and is deleted
  14 days later unless you upgrade it. It also has no backups and only 1 GB of
  storage.
- Free services have no shell access and no one-off jobs, so run console
  commands via Docker Compose locally or upgrade the service to a paid plan.

For anything beyond a demo, set `plan` to a paid value (for example
`0.5c-512mb` for the web service and `0.5c-1g` for the database) in
`render.yaml` and re-sync the Blueprint.

## Creating the first user

There is no registration endpoint yet. Generate a password hash locally:

```bash
cd backend
php bin/console security:hash-password
```

Then insert a row using the database's **external** connection string from the
Render dashboard:

```sql
INSERT INTO "user" (firstname, lastname, email, password)
VALUES ('Admin', 'User', 'admin@example.com', '<hashed password>');
```

Log in with `POST /auth` using `{"email":"admin@example.com","password":"..."}`
and send the returned token as `Authorization: Bearer <token>` to `/api` routes.

## Troubleshooting

- **Deploy fails with "Database is not reachable"** — confirm the service and
  database are in the same region and that `DATABASE_URL` points to the
  `iot-academic-db` internal connection string.
- **`Connection ... serverVersion` errors** — keep `DATABASE_SERVER_VERSION=18`
  (or match the major version you selected for the Render database).
- **401 on `/api`** — the `api` firewall requires a JWT. Use `/auth` first.
- **401 immediately after login** — `config/jwt/` keys changed after a restart;
  log in again, or switch to Secret Files as described above.
- **500 on `/measurements` on an older database** — the migration
  `Version20261124000000` creates that table; check the deploy logs to confirm
  migrations ran.
